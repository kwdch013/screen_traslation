# 実現可能性メモ

## 結論

リアルタイム画面翻訳アプリは実現可能である。

初期実装では、ゲーム画面を直接改変するのではなく、画面キャプチャ、OCR、翻訳、透過オーバーレイ表示を組み合わせる方式が現実的である。この方式ならゲーム本体への改造を避けられ、対象ゲームを広げやすい。

## 推奨する初期方式

```text
対象ウィンドウまたは画面領域
  -> キャプチャ
  -> 文字領域検出
  -> OCR
  -> 翻訳
  -> 表示位置決定
  -> 透過オーバーレイ
```

初期対象言語は英語のみとし、翻訳対象は字幕だけでなくUI全体まで広げられる構成を目指す。処理負荷が高くなる場合は、領域指定やOCR頻度制御で段階的に範囲を絞る。

## なぜオーバーレイ方式を優先するか

ゲーム内の文字をそのまま日本語に置き換えるには、ゲームごとの描画処理、フォント、テクスチャ、字幕UI、メモリ構造に依存する。汎用化が難しく、アンチチートや利用規約上のリスクも高くなる。

一方、オーバーレイ方式は画面の外側から日本語訳を重ねるため、対象ゲームへの依存を小さくできる。字幕の上から日本語を表示する要望にも近く、MVPとして検証しやすい。

## パフォーマンス見通し

想定GPUがRTX 5070 Ti 16GBで、対象ゲームのVRAM使用量が8GB以内程度であれば、残りのVRAMで軽量OCRと軽量翻訳を動かす余地はある。

ただし、GPU余力はゲームの解像度、描画負荷、フレームレート、使用するモデルによって大きく変わる。初期MVPでは次の制御を必須とする。

- 全画面ではなく字幕領域やUI領域に限定する。
- OCR頻度を毎フレームではなく、例えば5から10FPS相当に落とす。
- 画面差分が小さい場合はOCRと翻訳をスキップする。
- 同じ文字列は翻訳キャッシュを利用する。
- モデルは軽量なものから始める。
- 用語や固有名詞は辞書登録で補正する。

## 達成しやすいこと

- 字幕領域を指定して日本語訳を重ねる。
- 英語字幕を日本語として読みやすく表示する。
- ゲームごとの領域設定を保存する。
- 同じ字幕の再翻訳を避けて遅延と負荷を下げる。
- 速度優先、品質優先の設定を切り替える。

## 難しいこと

- ゲーム画面内の英語文字を完全に消して、日本語文字に自然に置き換える。
- 動きの激しい背景やエフェクト上の文字を安定してOCRする。
- あらゆるゲームのフルスクリーン表示で安定してオーバーレイする。
- アンチチートのあるゲームで確実に動作させる。
- 高精度なLLM翻訳を常時低負荷で実行する。

## 技術検証で確認すべきこと

### キャプチャ

- 対象ゲームの表示モードで画面取得できるか。
- キャプチャ遅延が許容範囲か。
- 領域指定によって負荷をどれだけ下げられるか。

### OCR

- 字幕フォント、背景、解像度ごとの認識率。
- 1回あたりの処理時間。
- GPU使用量とVRAM使用量。
- 同じ字幕の追跡と差分判定の精度。

### 翻訳

- 短文字幕の翻訳速度。
- キャッシュ適用後の体感遅延。
- 固有名詞やゲーム用語の扱いやすさ。
- ローカルモデルと外部APIの品質、速度、プライバシー差。

### オーバーレイ

- ボーダーレスウィンドウ、ウィンドウモード、フルスクリーンでの表示可否。
- クリック透過がゲーム操作を妨げないか。
- 日本語表示位置が字幕やUIと破綻しないか。
- 解像度変更、ウィンドウ移動、最小化への追従。

## 初期プロトタイプの合格基準

- 指定した画面領域の英語字幕を検出できる。
- 翻訳結果を1秒以内に日本語オーバーレイとして表示できる。
- 同じ字幕を繰り返し翻訳しない。
- 翻訳アプリ起動中でも対象ゲームの操作感が大きく悪化しない。
- ユーザーが翻訳対象領域と表示スタイルを調整できる。

## 現時点の判断

汎用的な「ゲーム画面の日本語化」アプリとしては、完全置換ではなくオーバーレイ翻訳から始めるべきである。

実現可能性確認の次段階では、実際のゲーム画面またはサンプル動画を使って、キャプチャ、OCR、翻訳、表示までの遅延と負荷を測定する。

UIはデスクトップアプリとして実装し、内部モジュールはキャプチャ、OCR、翻訳、辞書、オーバーレイ、設定に分離する。翻訳はローカル処理を基本とし、完全無料の外部APIだけを任意の差し替え先として扱う。
