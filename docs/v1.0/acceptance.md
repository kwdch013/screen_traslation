## 測定環境と画像集合

1. Windows 11 25H2 x64とLinux x86_64各1台以上、各4論理CPU/8 GiB RAM以上を使う。Linux代表はUbuntu 24.04 LTS、Docker Engine/Compose v2、Python 3.14。Tesseract、英語学習データ、Argos本体・英日モデルの版とSHA-256、コンテナdigest、SDK版、アプリSHAを固定・記録する。
2. CPUでOCR/翻訳する。サーバーは2 CPU/4 GiB、クライアントは512 MiB以内を監視する。専用GPUを使った結果は別枠。ホスト上の競合負荷を避け、CPU構成・メモリ量・画面解像度・DPI・Docker版など一般化した条件を記録する。IP・ホスト名・ユーザー名・鍵情報は記録せず、接続先/資格情報は外部設定から供給する。
3. 通常計測はLAN RTT p95 50 ms以下、実効10 Mbit/s以上、パケット損失0.1%以下の条件を満たした回だけ有効とする。RTTは同じ認証済み経路の往復を計測する。条件外は環境不成立として再試験し、性能合格にしない。通信障害試験は別に集計する。
4. `#109`で利用権を確認した200枚の固定集合を用意する。明瞭字幕100枚、複雑背景100枚（各群でメニュー25/会話25/動く背景25/小さい文字25）。1920×1080以内、各画像1～4行・20～200英字、文字高さ16～48 px、背景・フォント・句読点を混ぜる。ROI座標、正解原文、意味の基準、用語タグ、群、画像SHA-256をmanifestに記録する。難例・無文字・過大入力の別集合は品質の分母に混ぜない。
5. 既存 `src/tests/test_images/` は回帰の参考であり、それだけで上記200枚を満たしたことにしない。画像・正解・manifestの同一digestを3回とも使い、変更時は別の集合版で再評価する。試験用人工画像には個人情報を含めない。
6. 品質試験は全200枚を用いる。遅延試験は各群50枚の合計100枚を3巡し1回300件、3回の独立した測定を行う。無変化抑制に隠れないよう巡回ごとに画面を明示変更し、同一画面の重複送信を要求しない。5秒間隔で変更し、2 fpsで取得する。負荷試験は別途最大5 fps入力と最新1枚の置換を検証する。

## 計時・集計・判定

- クライアント内の単調時計で、フレーム取得開始から同フレームの訳文を実際に描画し終えた時点までを測る。画面変化→次回取得開始の待ちも別項目で報告する。サーバー内のOCR/翻訳時間も同一サーバーの単調時計で測り、異なる端末の時刻差を引かない。
- モデル導入済みで起動しready後、集合外の30フレームをwarmupする。測定中に再起動/モデル変更があればその回を無効化し、理由を記録してやり直す。描画完了までの相関IDはセッション/世代/フレーム/revisionで特定する。
- 300件を昇順に並べ、nearest-rank方式の `ceil(p × N)` 番目をp50/p95とする。未表示・処理失敗・期限切れは無限大として分母へ残す。各回でp50 ≤ 2000 ms、p95 ≤ 4000 ms、表示失敗率 ≤ 1%を満たす。成功分だけの参考値も報告できるが合否には使わない。
- OCRは正解と出力をUnicode NFCへ揃え、改行と連続空白を単一空白へ正規化し前後空白を除く。大文字小文字・句読点は区別する。CER =（文字の置換+削除+挿入）/正解文字数。群ごとの編集距離合計を正解文字数合計で割る。無出力は削除として含め、明瞭群5%以下、複雑群15%以下を判定する。
- 翻訳は固定100文（各群50文から抽出）を、主語・動作・対象・否定・数量を保持して利用者が意味を読めるかOwnerが判定する。可/不可と理由を文ごとに記録し、90文以上可、重大な意味逆転0件を求める。OCR原文と正解原文の両経路で確認し、OCR誤りを翻訳単体の誤りから区別する。20用語を含む全対象文で登録訳語が適用されることを確認する。
- CPUは1秒ごとに採取し、サーバーはcgroup制限2 CPU、Windowsは子プロセスを含む1分平均が全体比25%以下。メモリは1秒ごとの最大値（サーバーcgroupピーク4 GiB以下/Windows Private Bytes合計512 MiB以下）。8時間の開始10分後と終了前10分のメモリ中央値の増加を10%以下とし、OOM/クラッシュ/意図しない切断0件を確認する。
- 連続稼働はwarmup後8時間、2 fps、30秒ごとに集合画像を順送りする。各変更が期限内に表示されたかを分母にし、未表示・期限超過・エラーを失敗とする。失敗率1%以下。重複抑制を成功件数へ水増ししない。障害注入回は通常の遅延/連続稼働と分ける。
- 初回準備は空のモデル領域からダウンロード開始→検証→warmup→readyまで1800秒、導入済み再起動はプロセス起動→readyまで120秒。下り10 Mbit/s以上、モデル合計1 GiB以下を確認し、手動設定時間は別記する。配布物取得/依存ビルドはこの時間へ混ぜず、導入試験で所要時間を記録する。
- 閾値ちょうどは合格、1単位超は不合格。上限+1画素/バイト/接続、0サイズ、タイムアウト直前/直後、停止直前の結果を境界試験にする。入力契約の詳細値とエラー形式は #57/#62/#63 で定義する。

### ACC-02 停止・ホットキー・再選択と古い結果

- 前提: 翻訳中、遅延中の旧結果と100件以上の履歴を用意。REQ-F-006/007、REQ-NF-004。
- 操作: ボタン/ホットキーで停止し再開、別ROIに再選択する。停止/変更前の結果を後着させる。
- 期待結果: 停止から1秒以内に現在表示を消し、送信を止める。停止後は最大100件の履歴を閲覧できる。再選択/新セッションは履歴も消し、新世代だけ表示する。旧結果で復活しない。ホットキーの衝突/登録失敗は状態と代替ボタンを示す。
- 担当: #73/#78/#98/#100、独立担当、Owner。

### ACC-03 選択取消・対象消失・取得不能

- 前提: 選択前、取得中、取得制限された対象をそれぞれ用意。REQ-F-001/006。
- 操作: 選択を取消、取得中の対象を閉じる/最小化、取得不能/保護された対象を選ぶ。
- 期待結果: 取消で送信しない。無効化した対象の送信を止め、検知から1秒以内に表示を消す。理由と再選択を案内し、他画面へ暗黙に切り替えない。保護機構の回避はしない。
- 担当: #58/#92/#95/#98、独立担当、Owner。
- 証跡: 対象種別、状態遷移、取得回数、表示消去時間、対応外の説明。

### ACC-04 切断と復旧・期限切れ

- 前提: 翻訳中。REQ-F-009、REQ-NF-004。
- 操作: ネットワークを遮断して戻す。通信が続いていてもフレーム結果だけを5秒以上遅延させる。サーバーも再起動する。
- 期待結果: 無通信から5秒以内に切断を検知し、その1秒以内に表示を消す。接続復旧だけで画像送信しない。利用者の明示開始後に新セッション/世代で再開する。取得から5秒を過ぎた表示/結果は消去・破棄し、旧応答で復活しない。
- 担当: #73/#79/#89/#90/#108、独立担当、Owner。

## ユーザー追加シナリオとリリース判定

Ownerは実際の使い方で少なくとも1件を追加する。独立担当が再現可能性を補助し、`USR-01`から採番、要件ID・前提・操作・期待結果・対象SHA・実績・本人判定を記載する。未作成の場合も未実施であり、必須シナリオを消して置換しない。
